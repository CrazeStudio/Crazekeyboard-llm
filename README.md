# CrazeLM — Final 30M Architecture

CrazeLM is an English causal Transformer intended to provide next-word candidates for CrazeKeyboard. This repository contains the model, tokenizer training, corpus preparation, Kaggle training, evaluation, and prediction tools.

> **Important:** The architecture target is implemented in code. The final tokenizer, trained weights, keyboard ranking layer, and Android runtime are not produced automatically. A 100k tokenizer requires a large and diverse corpus; the current DailyDialog-only corpus is not sufficient for the tokenizer's 100-million-character minimum.

## Final architecture

| Component | Setting |
|---|---:|
| Vocabulary | Exactly 100,000 SentencePiece pieces |
| Transformer layers | 5 |
| Model width | 256 |
| Attention heads | 8 |
| FFN width | 1,024 |
| Context length | 128 tokens |
| Embedding/output weights | Tied |
| Expected parameters | 29,582,080 (about 29.6M) |
| Language | English |

The embedding table accounts for most parameters: 100,000 x 256 = 25.6M. The remaining parameters are in the five Transformer blocks, positional embeddings, and normalization layers. The model inspector and training script verify the parameter count. If you change the vocabulary size, the parameter count changes.

**Why this shape:** With tied embeddings, a 100k vocabulary and 256-wide embedding already use 25.6M parameters. A much wider model would exceed the 30M target. The selected 5-layer configuration keeps the total close to 30M.

## Token storage

The old pipeline stored token IDs as unsigned 16-bit integers. That cannot represent a 100,000-piece vocabulary. The updated training pipeline uses **uint32** for on-disk token streams and converts sampled batches to int64 for PyTorch. Do not reuse old train_tokens.bin or val_tokens.bin files generated by the previous 8k model.

## 2. Prepare a sufficiently large corpus

The existing downloader prepares DailyDialog conversational data:

    !python scripts/prepare_dataset.py --output_dir /kaggle/working/crazelm_data --min_train_lines 50000

DailyDialog is useful for conversational style, but it is not enough by itself for the final 100k vocabulary. The tokenizer trainer deliberately refuses corpora smaller than **100,000 non-empty lines and 100 million characters**. That is a conservative minimum guard, not a guarantee that the corpus is good enough.

Before training the tokenizer, build a larger, diverse, properly licensed English corpus. It should include conversational text, natural sentences, questions, common phrases, varied writing styles, and correctly punctuated text. Keep separate train, validation, and test splits. Do not mix validation/test material into training, and do not duplicate lines to inflate the corpus. Keep source names, licenses, attribution requirements, and counts in a manifest. Do not redistribute data unless its license permits it.

The final dataset should be much larger than 50,000 utterances. A 30M model trained on a tiny corpus will overfit regardless of the parameter count.

## 2A. Add a larger English source: WikiText-103

The DailyDialog mirror alone is too small. Add WikiText-103 from Salesforce, which contains over 100 million Wikipedia-derived tokens and has separate train/validation/test splits. The Hugging Face card lists CC-BY-SA-3.0 and GFDL metadata, while its prose also references CC BY-SA 4.0. Review the card and original Wikipedia terms, preserve attribution, and understand share-alike obligations before redistribution.

Pull the latest repository and run:

    !git pull origin main
    !python scripts/add_wikitext.py --corpus_dir /kaggle/working/crazelm_data --cache_dir /kaggle/working/wikitext_downloads --min_added_train_chars 100000000

This downloads the two training Parquet shards and the validation/test shards, reads them in batches, normalizes text, filters obvious markup/short fragments, and performs disk-backed exact case-insensitive deduplication within each WikiText split. It writes separate wikitext103.txt files into the existing train, validation, and test directories, so the existing DailyDialog text remains present and the training scripts discover both sources recursively. Downloaded Parquet files and the SQLite deduplication indexes are cached separately.

Check the combined corpus:

    from pathlib import Path
    for split in ["train", "validation", "test"]:
        folder = Path("/kaggle/working/crazelm_data") / split
        files = list(folder.glob("*.txt"))
        lines = sum(sum(1 for x in f.open(encoding="utf-8") if x.strip()) for f in files)
        chars = sum(len(f.read_text(encoding="utf-8")) for f in files)
        print(split, "files:", [f.name for f in files], "lines:", lines, "characters:", chars)

Do not proceed unless the training corpus meets the tokenizer script's 100,000-line and 100-million-character guards. These are minimum checks, not proof of sufficient linguistic diversity. Keep validation and test data out of tokenizer/model training.

## 3. Train the exact 100k tokenizer

Run this only after the training corpus has enough genuine data:

    !python scripts/train_tokenizer.py --input_dir /kaggle/working/crazelm_data/train --output_dir /kaggle/working/tokenizer --vocab_size 100000

The script uses SentencePiece BPE with byte fallback and a hard vocabulary limit. It fails rather than silently creating a smaller vocabulary. Check that the printed vocabulary is exactly 100,000.

## 4. Train the final 30M model

The updated defaults are 10 epochs, 2,000 steps per epoch, batch size 8, context 128, and learning rate 0.0002. For a serious final run, increase training steps based on corpus size and validation results; the defaults are a starting run, not a claim that the model is fully trained.

    !python train.py --train_dir /kaggle/working/crazelm_data/train --val_dir /kaggle/working/crazelm_data/validation --tokenizer /kaggle/working/tokenizer/tokenizer.model --output_dir /kaggle/working/crazelm_30m --epochs 10 --batch_size 8 --seq_len 128 --steps_per_epoch 2000 --eval_steps 50 --save_every 250 --lr 0.0002

If CUDA runs out of memory, reduce batch size to 4 or 2. This reduces throughput but preserves the model shape. Do not reduce vocabulary size if the 100k requirement is fixed. Save/download checkpoints regularly because Kaggle sessions are temporary.

The script writes:
- best.pt — checkpoint with the lowest observed validation loss
- last.pt — latest checkpoint
- model_config.json — exact architecture and parameter count
- metrics.jsonl — validation history
- train_tokens.bin and val_tokens.bin — uint32 token streams

The current trainer starts a fresh run; it does not resume optimizer state. Use a new output directory when changing tokenizer or architecture. Do not load old 10M checkpoints into this 30M architecture.

## What is and is not finished

Implemented in the repository:
- 30M-class model architecture with a 100k vocabulary target
- uint32 token storage for IDs above 65,535
- tokenizer size enforcement
- training, checkpointing, evaluation, and prediction scripts
- parameter-count and weight-size inspection

Still required before calling CrazeLM production-ready:
- a large, diverse, appropriately licensed English corpus
- a completed long training run with stable held-out metrics
- word-level candidate assembly and keyboard-specific ranking
- real typing benchmark for top-1/top-3/top-5 suggestion accuracy
- autocorrect and typo correction
- privacy-preserving on-device personalization
- quantization/export and Android inference integration
- on-device latency, RAM, battery, and crash testing

**This is the final architecture target, not a finished trained model.** The 100k tokenizer and trained weights must still be generated and evaluated in Kaggle. Do not describe it as production-ready until the remaining work passes testing.


## 8. Export the v1.0 release to ONNX

The repository includes a GitHub Actions workflow at `.github/workflows/export-onnx.yml`. Run it from **Actions → Export CrazeLM ONNX → Run workflow**. It downloads the pinned release archive:

`https://github.com/CrazeStudio/Crazekeyboard-llm/releases/download/v1.0/CrazeLM-30M-v1.0.zip`

The workflow extracts the archive, selects `best.pt` when present (otherwise the first `.pt` checkpoint), exports a compact FP16 graph to `CrazeLM-30M-v1.0-fp16.onnx`, validates the ONNX graph, and runs numerical parity tests against PyTorch on several batch and sequence sizes. It uploads the ONNX file, original ZIP, and SHA-256 checksums as a workflow artifact.

To export locally:

```bash
pip install -r requirements.txt
pip install "onnx>=1.16" "onnxruntime>=1.18" "pytest>=8"
unzip CrazeLM-30M-v1.0.zip -d release
python scripts/export_onnx.py --checkpoint release/path/to/best.pt --output CrazeLM-30M-v1.0-fp16.onnx
CRAZELM_CHECKPOINT=release/path/to/best.pt CRAZELM_ONNX=CrazeLM-30M-v1.0-fp16.onnx pytest -q tests/test_onnx_export.py
```

The compact FP16 ONNX graph stores internal weights/compute in FP16 (with int64 token IDs and FP32 logits at the public interface) and accepts `input_ids` and returns `logits` with shape `[batch, sequence, 100000]`. The exporter also deduplicates byte-identical initializers, including CrazeLM's tied input/output embedding weights, so those weights are not stored twice. FP16 weight storage is approximately half FP32; actual file size depends on graph overhead and the release checkpoint. CI enforces an export smaller than 100 MiB. The sequence length may vary up to the checkpoint's configured maximum (128 for the current target). The SentencePiece tokenizer is still required by the Android app to turn text into token IDs and decode predicted token IDs.

This workflow produces an ONNX model artifact; it does not yet integrate ONNX Runtime into the Android keyboard app or implement word-level suggestion ranking.


### Supported PyTorch artifact types

The exporter does not assume that a `.pt` file is a training-checkpoint dictionary. It attempts, in order:
1. TorchScript serialized module
2. Full `torch.nn.Module` saved with `torch.save`
3. Training checkpoint containing `model` and optional `config`
4. Raw tensor `state_dict` matching the repository's default CrazeLM architecture

A bare state dict has no architecture metadata, so the default 30M configuration is used and strict weight loading must match exactly. If the `.pt` contains a complete module, its forward output is normalized to logits. Unsupported payload types and incompatible weights fail with a diagnostic rather than silently exporting random weights.
